# Handoff: Bogenzeit + Tagbogen

You are picking up a design that is finished on paper. Your job is to build it. Read this file first, then the specs in order.

## What this is

- **Bogenzeit (BZ)** — a personal time standard. Time is read as position on the Sun's arc, not as hours and minutes. Anchors: solar noon (☉) and solar midnight (○). Units: **spans** (100 per half-arc, proportional, length varies with season) and **kiloseconds** (fixed). Eight named quarters. Linked to UTC; computed from UTC instant + GPS coordinates.
- **Tagbogen** — the watch face / app family that displays Bogenzeit. Several dial variants; tap to see civil time.

## Read in this order

1. `docs/bogenzeit-spec.md` — the time standard. **Normative.** Do not change definitions without asking David.
2. `docs/tagbogen-spec.md` — the face/app: platforms, interaction, variants, onboarding topics.
3. `reference/bz_reference.py` — prototype implementation in stdlib Python. Defines the algorithm precisely.

5. `design/mockups/*.svg` — static mockups of dial variants 1 and 2, Bogenzeit and civil views (Houston, 1 Nov 2026, 11:08 CST). Live canvas: https://claude.ai/artifact/6dZm44VVzeidpq1taGMp2m

## Rules that are easy to get wrong

- **Rounding:** displayed spans and ks are the **floor of the signed value** (toward the past). 59.3 spans before ☉ shows `60 ☉`. `☉` appears only from exact solar noon; sunset only at exact sunset. (BZ §5.2)
- **Notation:** position replaces sign. Number left of glyph = before, right = after: `18 [3.43 ks] ☉`, `☉ 3 [0.70 ks]`. No `+`/`−`, no middle dot, no `~`. (BZ §3.2, §3.7)
- **Date switchover at solar midnight (○)**, not civil midnight. Day includes its starting ○, excludes its ending ○. (BZ §5.1)
- **Quarter boundaries:** start inclusive, end exclusive; exactly ☉ is Afternoon. Boundaries have no names. (BZ §3.6)
- **Glyphs ☉ and ○ are drawn as vector shapes from one shared circle definition**, never rendered from a font: no font draws them at matching sizes. (BZ §3.1)
- **No hours or minutes** anywhere in the Bogenzeit view. Civil time appears only in the tapped civil view.
- **Elevation and terrain are ignored.** Sea-level horizon, −0.833°. (BZ §5.4)
- **Polar day/night:** spans and quarters are undefined; show ks offsets only. (BZ §3.5)
- **Offline:** all computation on the watch. No network.
- **Location:** recompute when moved > 10 km, and at least once per solar day. (BZ §5.5)

## Platform facts (verified Nov 2026)

- **Apple Watch:** third-party watch faces are not allowed. Tagbogen is a watchOS app + WidgetKit widgets/complications (Smart Stack, accessory families).
- **Wear OS:** as of January 2026 only **Watch Face Format (WFF)** faces install from Play. WFF is declarative XML with no executable code, and the AndroidX watch face APIs are deprecated — but the **complication APIs remain supported**, and **Watch Face Push** lets an app install a face programmatically. Implication: the Bogenzeit computation must live in a Kotlin app (complication data sources and/or tiles); the WFF face renders what it's given. **Investigate first** what WFF can draw from complication data (ranged values, text, expressions) before committing to the dial designs; report back limits to David.

## Proposed architecture

```
bogenzeit/
  core/        Rust crate `bz` + CLI `bz` (reference-grade; passes vectors)
  vectors/     golden vectors (shared contract)
  apple/       watchOS app "Tagbogen" (SwiftUI) + WidgetKit; Swift port of the engine
  wear/        Kotlin engine port + complication data sources/tiles + WFF face(s)
  docs/ design/ reference/
```

Engine ports are small (a few hundred lines). Recommended: implement natively in each language and hold them together with the shared vectors, rather than an FFI layer. If you see a strong reason for one shared Rust core via UniFFI, propose it to David before building it.

## Phases

1. **Engine + CLI.** Rust `bz` crate and `bz` CLI (`bz now --lat --lon`, `bz at <utc> --lat --lon`, `bz day <date>` table of events/quarters). Passes all vectors. Add vectors for edge cases you find (leap years, date-line longitudes, southern hemisphere, polar transitions).
2. **Apple Watch app.** Swift engine port (passes vectors). App with dial variants 1 (fixed-time) and 2 (span), tap for civil view, onboarding explainer (topics in Tagbogen spec §5). Widgets/complications: at least span readout, quarter name, and a small arc gauge.
3. **Wear OS.** Kotlin engine port (passes vectors). Complication data sources exposing span, ks offset, quarter, anchor, Tagbogen/Nachtbogen lengths. WFF face(s) reproducing variants 1 and 2 as closely as WFF allows.

David decides the order of phases 2 and 3; ask before starting either.

## Acceptance (per platform)

- Passes `vectors/bz_vectors.json` (event times within 1 s; displayed values exact).
- Houston 1 Nov 2026 17:08 UTC renders `18 ☉`, `[3.43 ks]`, `Forenoon`; tap shows `11:08`, `CST | UTC−6`.
- Display changes exactly on boundaries (floor rule), verified by a test that steps through a boundary.
- ☉ and ○ render at identical size.
- Works offline; recomputes on location change per the 10 km rule.
